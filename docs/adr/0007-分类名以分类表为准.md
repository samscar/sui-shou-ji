# 分类名以分类表为准，自定义映射不得引入新分类

Status: accepted

## 背景与决策

分类映射的下拉框里同时出现了「交流通信」与「交流通讯」两个并列主分类，内容一模一样
（手机话费：广东移动、中国电信）。前者来自内置分类表，后者是凭空长出来的。

成因是一次笔误被固化：内置分类表原本写作「交流通信」（随手记的官方一级分类是
**交流通讯**，此处是建表时的笔误），用户在「编辑分类表」里把它改成了「交流通讯」并保存。
保存时的差异比对把「分类表里没有的关键词」转成自定义映射词条，于是 `交流通讯 / 手机话费`
下的两个关键词被写成两条自定义映射；此后每次启动合并，`mergeConfigs` 都对缺失的主分类
执行 `categories[mainCategory] = {}`，把这个笔误重建为一个合法分类。用户在界面上既看不出
它是假的，也删不掉它。

决策：**分类名只有一个权威来源——内置分类表。** 自定义映射只能往已有的主分类与子分类里
添加关键词，不能创建分类。校验分两层：

- **写入侧拒绝。** 「保存并生效」与「导入配置」在落盘前校验，出现分类表里没有的主分类或
  子分类时中止，并列出违规项。这是用户还能改的时刻，必须报错而不是吞掉。
- **读取侧丢弃。** `mergeConfigs` 面对已经存在本地的脏数据，丢弃引用不存在分类的映射
  并在控制台留一条告警。不能在这里抛错——那会让应用直接打不开。

行为上的代价必须知情：**分类表改名会让引用旧名的自定义映射失效。** 例如把「交流通讯」
再改成别的名字，指向旧名的那几条映射会在下次启动时被丢弃，需要重新添加。

## 为什么不允许用户自由新建分类

随手记支持手动添加分类，所以「允许自由命名」看起来顺理成章。放弃的理由：

- **按分类名判断的逻辑会静默失效。** 出行区间的居家支出白名单
  （`HOME_MAIN_CATEGORIES`，见 ADR-0006）是按主分类名比对的。`交流通信` 与 `交流通讯`
  只要差一个字，手机话费就掉出白名单，出行区间会把它当成旅游花销改判——没有任何报错。
- **分类表快照会传播笔误。** 导出的是合并后的分类表，幽灵分类会被写进文件；换台设备导入
  时又被差异比对重新固化一次，越传越牢。对齐分类表是快照能跨设备使用的前提。
- **重复关键词的命中顺序不可预期。** 解析用 `Map.set` 构建关键词表，后写入的覆盖先写入的。
  同一关键词挂在两个分类下时，哪条生效取决于合并顺序，而不是谁的意图更明确。

## 考虑过的其他方案

- **只在读取侧丢弃，写入侧不动。** 放弃。用户的编辑看起来保存成功了，实际上被悄悄丢弃，
  下次导出时才发现少了东西——错误必须在能修改的时候暴露。
- **自动把未知分类名纠正到最相近的已有分类。** 放弃。编辑距离最接近的候选很可能不是本意，
  猜错比报错更难排查。
- **把分类名也纳入「用户修改」，允许覆盖内置分类表。** 放弃。那等于把分类表变成两份可写的
  真源，冲突时的优先级规则用户看不见，与 ADR-0002 让用户修改只承担「增量」的定位相悖。

## 后果

- 内置分类表里的「交流通信」更正为「交流通讯」（与随手记一致）。`trip.ts` 的居家支出白名单、
  `scripts/verify-trip.ts`、ADR-0006 中的同名字样一并更正。
- 导入旧快照时，含「交流通信」等笔误分类的文件会被拒绝，并列出具体是哪一条主分类/子分类。
  需要手工改正后重新导入——这是有意的：让脏数据进不来。
- `scripts/verify-config.ts` 覆盖上述约束，`npm run verify` 现在包含它。
- 已知遗留：分类表**只增不减**。差异比对只收集「比内置表多出来的关键词」，从不处理删除，
  因此想删掉一个分类仍然只能手改 JSON 文本。本次不处理，见后续 issue。
