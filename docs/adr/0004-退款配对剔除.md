# 退款配对后成对剔除，不计入账单

Status: accepted

## 背景与决策

一份真实流水（298 笔，2026-09-01 ~ 2026-10-07）里有 44 笔退款、合计 8,156.73 元，
占该期支出的 4.44%。它们全部是 `摘要 = 消费退货` 的正向入账。按金额符号分流，
现状会把一笔 500 元消费记成「支出 500 + 收入 500」：净额为零，但两个科目各自被抬高 500，
导致「某个分类本月花了多少」这个数字长期虚高，而退款本身也堆在「待分类收入」里等人手工处理。

决策：在分类之前先做**退款配对**。配对成功的流水成对剔除，不进入随手记账单；
配对失败的退款保持原样，仍作为收入记录进入待分类列表，与改动前行为一致。

配对只有两层：

1. **全额 1:1** —— 商户相同、金额绝对值相等、出账日期不晚于退款日期。
   多个候选时取日期最近的一笔。歧义候选通常同额同商户同分类，指派给哪一笔都不改变分类总额。
2. **全额 1:N（拆分退款）** —— 同一商户下多笔退款合计等于一笔出账。
   本样本有 4 组：628 = 314×2、588 = 294×2、149 = 74.50×2、119 = 59.50×2，共 8 笔退款。
   若要求逐笔金额相等，这些永远配不上，而火车票退票正是本期退款最密集的场景。

**金额不相等的场景不配对。** 部分退款（退 271、原单 313.06）不做处理，两笔都留在账单上。
曾考虑过"删除配对并把差额记为「其他杂项 / 退款折损费」"，放弃的理由见下。

## 硬约束（数据实测得出，不是个人偏好）

- **退款语义只认摘要列。** 这 44 笔退款的附言里，`退款`、`退货`、`撤销`、`冲正`、`退回`
  命中 0 次。任何只扫备注的实现，在本样本上得到 0 条退款。
- **出账日期不晚于退款日期是硬条件。** 缺了它，09-18 的 `+18.00` 会配到 10-05 的两笔
  无关消费上。一笔退款不可能由未来的消费导致。
- **商户名不能用「对方账号与户名」单列判定。** 298 行里有 241 行（81%）的出账记录户名
  被打码成 `***公司`、`**转账`、`***商户`，而退款行的户名是完整的。可行的口径是取两侧
  商户名候选的并集再求交集：户名（未打码时）∪ 附言的最后一段（剔除「消费」「转账」
  这类通用词）。
- **「微信转账」必须留在可匹配的商户词里。** 它是渠道词不是商户名，但充值退款的附言
  两边都只有它，排掉会让「充值 -204.00 ↔ 退款 +204.00」这类合法配对全部落空。
- **不按「金额 + 商户 + 日期」去重。** 314、294、11.50、59.50 的成对重复行都是真实入账，
  余额逐行勾稽可证。任何去重都会删掉真钱。

## 考虑过的其他方案

- **记收入（现状）。** 这是 12 个主流记账产品里唯一明确错误的做法（鲨鱼记账）。GnuCash
  官方文档把它直接列为常见错误；IFRS 15 与《企业会计准则第 14 号》的口径一致——
  退款是收入的减项，不是收入。分类支出与总收入会同时虚高，误差不会随时间自愈。
- **净额法：退款冲减原分类、保留原单（YNAB / Actual / GnuCash / 随手记 / 钱迹的做法）。**
  这是行业压倒性共识，也是唯一能同时保住「分类净额」与「原始流水可追溯」的做法。
  不采用的原因：目标产物是随手记的三表模板（支出 / 收入 / 转账），模板里没有"退款"的
  位置；要用负金额的支出行表达，随手记能否接受未经验证（官方帮助中心已 404）。
  待该问题验证通过后，值得重开这条。
- **删除配对 + 差额记「其他杂项 / 退款折损费」。** 放弃。数据里差额的两种性质算法分不出来：
  `买 313.06 退 271` 是"留用了 42 元的商品"，属于真实消费；`退票只退一部分` 才是手续费损失。
  把两者都塞进损失科目，等于把真实消费从购物、餐饮搬到杂项，是另一个方向的失真。
- **任意金额凑单（子集和，不限商户）。** 实测会把三笔互不相干的消费拼成一笔退款：
  `+271.00` 凑成「微信转账 218 + 淘宝 38 + 好食惠简餐 15」；`+124.00` 凑成
  「美团 12.10 + 贵州高速 53 + 天猫资生堂 58.90」。加上同商户约束后产出一笔也不多。
- **纯金额兜底（金额相等即可配对，不看商户）。** 实测在这份样本上只找到 1 对，
  且 1 对全错：`09-28 +5.00 广记昌` 配到 `09-25 -5.00 成都豪腾`。零正确产出，已移除。
- **跨文件配对。** 不做。本期有 5 笔退款的原单在上个月或别的渠道
  （09-01 的视频号小店 13.90、09-11 的深圳鲜语 138.00）。保留为收入反而正确：
  上月已记支出、本月记收入，两个月净额归零；剔除会让本期凭空少一笔真实入账。
- **只在候选唯一时才剔除。** 数据否掉了这条保守路线。119 元有 7 笔出账对 5 笔退款、
  149 元有 8 对 5，要求唯一则这 10 笔退款永远清不掉；而这些候选同金额、同商户、同分类，
  按日期最近指派在报表上等价于正确配对。

## 后果

- 本样本：第一层 22 对、第二层 4 组，剔除出账合计 **7,392.88**。
  应用内支出 133,904.09 → **126,511.21**，收入 102,166.10 → **94,773.22**，两者同步下降
  7,392.88（净额不变，这正是配对成立的前提）。
  注意口径：银行表头的「总支出 183,904.09」含跨行转出 50,000，与应用内的支出桶不是一回事，
  不能直接相减；同口径下降后是 176,511.21。
- 44 笔退款中 30 笔回落，14 笔未配对。未配对的 14 笔合计 763.85 元（占退款总额 9.4%），
  其中只有 3 笔超过 100 元（271 / 138 / 124），其余 11 笔合计 230.85。
  它们仍进「其他收入 / 收入」待分类，是有意保留的噪音：确实还没找到归属。
- 剔除是启发式判断，必须可撤销。页面上单列「剔除清单」，逐条可恢复；
  恢复时重新解析，行为可预期。
- 与 ADR-0001 / ADR-0003 的交付形态无关：本改动只影响解析层，不改变产物形态。
