# 出行区间：按日期批量改判支出分类，界面改为 Tab

## Problem Statement

用户每次出游或出差回来，把建设银行流水导进应用，都会撞上同一件事：这一趟的花销散在七八个分类里。
一份真实的 298 行流水里，2026-10-01 ~ 10-06 这六天有 67 笔支出、合计 ¥14,894.37，其中
**44 笔 ¥2,233.28 落在「其他杂项」**，正等着人一条条点「编辑」；另外 22 笔散在「购物消费 / 日常购物」
「食品酒水 / 日常餐饮」「行车交通 / 打车」「出差旅游 / 交通费」里。想回答"这趟一共花了多少"，
只能手工改几十次分类。

同一份流水导入后，页面自上而下是：3 张统计卡、2 个按钮、待分类支出表（97 行）、退款剔除清单（26 行）、
待分类收入表（15 行）、转账表（2 行）、7 条使用说明。纵向长度超过 1000 像素，四张权重相同的表格
堆在一起，越往下越难找到要看的那一张。

## Solution

两件事，一次交付：

1. **出行区间**。用户手动选择起止日期，区间内的支出（固定支出除外）整体改判为
   「出差旅游 / 其他消费」。改判结果单独成表（区间归类清单），逐条列出日期、金额、原分类、备注，
   每条可「不计入」、也可恢复。
2. **界面改为 Tab**。概览 / 待分类 / 退款剔除 / 转账 / 出行区间，每张表各归其位。

## User Stories

1. 作为记账用户，我想手动选择一次外出的起止日期，这样我不必逐笔修改这几十笔支出的分类。
2. 作为记账用户，我想让区间内的支出统一归入「出差旅游 / 其他消费」，这样我在随手记里能一眼看到这趟花了多少。
3. 作为记账用户，我想让房贷、物业水电、手机话费、网购与超市采买这类居家支出不被改判，这样旅游支出不会因为一笔一万块的房贷或一单寄回家的床垫而虚增。
4. 作为记账用户，我想看到区间内被改判的每一笔支出（日期、金额、原分类、备注），这样我能核对系统没有乱改。
5. 作为记账用户，我想把清单里的某一条标为「不计入」，这样系统判断错的那一笔不会污染总额。
6. 作为记账用户，我想把已标「不计入」的一条恢复回来，这样我点错了还能改。
7. 作为记账用户，我想在区间生效时看到一句汇总（区间、笔数、合计金额），这样我能确认自己选的是这两组日期。
8. 作为记账用户，我想随时清除区间，这样所有记录回到关键词与交易修正记录给出的分类。
9. 作为记账用户，我想让区间的结果不写进浏览器存储，这样它不会变成一条我以后还要管理的长期规则。
10. 作为记账用户，我想在界面上知道区间刷新后会失效，这样我不会在导出前误以为它还在生效。
11. 作为记账用户，我想让区间内的工资收入保持原分类，这样收入不会被算成旅游支出。
12. 作为记账用户，我想让退款配对的结果不受区间影响，这样已剔除的退款不会因为区间又被算回支出。
13. 作为记账用户，我想让区间只改变分类、不改变金额合计，这样统计卡上的支出总额仍然可信。
14. 作为记账用户，我想在起止日期填反时无法应用，这样我不会选中一个空区间还以为是没数据。
15. 作为记账用户，我想在区间内没有支出时看到明确提示，这样我知道是这段日期确实没消费，不是操作失败。
16. 作为记账用户，我想用 Tab 在概览、待分类、退款剔除、转账、出行区间之间切换，这样我不用滚过一千像素找表格。
17. 作为记账用户，我想每个 Tab 上带笔数，这样我在切走之前知道那边还有多少东西没处理。
18. 作为记账用户，我想某个 Tab 没有数据时它变灰但位置不动，这样 Tab 的顺序不会跳来跳去。
19. 作为记账用户，我想导出按钮在任何 Tab 下都点得到，这样改完最后一笔不用先切回概览。
20. 作为记账用户，我想在概览里看到一句待办摘要（待分类多少笔、区间生效多少笔、退款剔除多少对），并且能点进去，这样我不会忘记某张表还没看。
21. 作为记账用户，我想使用说明默认收起，这样它不再占一整屏。
22. 作为记账用户，我想在重新导入文件后区间被清空、页面回到概览，这样上一份流水的选择不会污染这一份。
23. 作为记账用户，我想在区间 Tab 里看到"居家支出不会被改判"的说明，这样我不会怀疑系统漏改了几笔。
24. 作为记账用户，我想在区间清单里按日期顺序阅读，这样我能对着行程回忆每一笔花销。
25. 作为维护者，我想让全部归类行为仍然只从一个入口出去，这样新增一条归类规则时不必在多处同步修改。
26. 作为维护者，我想让界面按 Tab 拆成组件，这样主界面文件不再继续长成两千行。
27. 作为维护者，我想让区间规则不进入用户修改的存储结构，这样"用户积累的数据"仍然只有两类：自定义映射词条与交易修正记录。

## Implementation Decisions

### 解析层

- **单一入口**：`parseCCBData` 增加一个可选参数 `trip`，包含 `range`、`target`、`fixedMainCategories`、
  `excludedKeys` 四项。现有四个参数与返回值中的既有字段行为不变；**不传 `trip` 时，结果必须与改动前逐字节一致**。
  返回值新增 `tripRecords: TripRecord[]`，未启用区间时为空数组。
- **套用顺序**：退款配对 → 关键词匹配 / 交易修正记录 → 出行区间。
  区间放在后一层是刻意的：先拿到"原本会是什么分类"，清单里才有可退回的地方。区间因此会覆盖交易修正记录，
  但撤销一条即自动退回修正记录给出的分类，两个概念不互相污染。
- **居家支出按主分类判断**，集合为「金融保险」「居家生活」「交流通信」「购物消费」，判定时点取关键词或修正记录
  给出的分类，**不看摘要**。理由：`摘要` 列无法区分消费与非消费——`跨行转出` 既包含还房贷也包含红包，
  `充值` 的 8 笔全是扫码付款给个人，`消费` 覆盖不到前两类。
  购物消费在其中，是因为旅途期间的网购是日常行为，不因下单地点在酒店而变成旅游花销。
- **闭区间**：按交易日期前 10 位（`YYYY-MM-DD`）比较，忽略时分秒，起止两天整天含入。
- **只作用于支出**：收入与转账的代码路径不接触 `trip`。退款配对发生在更前一层，同样不受影响。
- **目标分类固定**为「出差旅游 / 其他消费」，不做下拉框。
- **撤销键**：`行号 + 备注 + 交易日期`。只用「备注 + 交易日期」不够——同一商户同一天可能有两笔同额消费
  （真实流水里 10-05 就有两笔 ¥5.00 的牛肉粉），撞键会让撤销一笔连带另一笔。行号在同一份文件内稳定。
- **状态不落盘**：区间不写入 `UserConfig`，不进入 localStorage，不进入分类表快照。它是会话内的临时选择，
  与"剔除清单里恢复了哪几对"同类。

### 界面层

- **状态归属**：全部状态与流程编排留在主界面文件，组件只接收 props，不引入 context。
- **样式**：现有样式常量原样搬到一个独立的样式模块，值一个不改。
- **Tab 顺序**：概览 / 待分类 / 退款剔除 / 转账 / 出行区间。出行区间排最后——它是偶发操作，不是每月必经的步骤。
- **Tab 计数**：待分类 = 支出待分类 + 收入待分类；退款剔除 = 配对数；转账 = 笔数；出行区间 = 被改判笔数
  （未选区间时不显示计数）。计数为 0 时不显示数字。
- **空 Tab**：没有数据的 Tab 置灰不可点，但保留占位，避免 Tab 顺序跳动。「所有记录已分类完成」的提示移到概览。
- **默认 Tab**：概览。解析完成、切换文件、导入配置后一律重置到概览。
- **导出按钮**常驻 Tab 栏右侧，任何 Tab 下都可点击。
- **概览内容**：三张统计卡（支出 / 收入 / 转账）、待办摘要（可点击跳转到对应 Tab）、导出按钮、折叠收起的使用说明。
- **出行区间 Tab**：起止日期输入、应用 / 清除按钮、生效后的汇总行、区间归类清单（日期 / 原分类 / 子分类 / 金额 / 备注 / 操作）。
  起止任一为空、或起点晚于终点时，「应用」不可点。区间内没有支出时给出明确空状态文案。

### 文档

- `CONTEXT.md` 新增「出行区间」「固定支出」「区间归类清单」三个词条。
- `docs/adr/0006-出行区间一次性批量改判.md` 记录三条决定的理由：为什么一次性、为什么按主分类排除固定支出、
  为什么必须给可撤销清单。
- `README.md` 的「使用步骤」「目录结构」随新界面与新模块同步更新。

## Testing Decisions

- **好的测试只验证外部行为**：喂一批流水记录给解析入口，断言输出的分类与 `tripRecords`。
  不断言内部函数、不依赖实现顺序。
- **唯一接缝**：`parseCCBData`。这是归类行为的最高入口，现有 `verify:refunds` 也走这条线
  （先例：`scripts/verify-refunds.ts` 用合成样本 + 计数断言 + 失败退出码）。不新增第二层接缝。
- **新增回归脚本**：`scripts/verify-trip.ts`，用合成样本覆盖以下行为：
  - 端点日含入（起始日与结束日各一笔都应改判）
  - 区间外一天的同额记录不动
  - 固定支出（房贷）不被改判，购物消费（网购）也不被改判，其余照改
  - 已标记「不计入」的条目保持原分类
  - 交易修正记录先被判出、再被区间覆盖，撤销后退回修正记录的分类
  - 不传 `trip` 时行为与改动前一致
  - 跨边界的退款配对不受区间影响
  - 收入与转账的笔数、金额、分类不受区间影响
- **回归门槛**：`npm run verify:refunds` 必须仍然全部通过。改动解析层后先跑它。
- **真实流水对账**（人工、一次性）：区间 `2026-10-01 ~ 2026-10-06` 应改判 **54 笔 ¥3,119.07**；
  保持不动 **13 笔 ¥11,775.30**（含房贷 ¥10,400.00、话费 ¥199.59，以及 11 笔购物消费 ¥1,175.71）。
- **界面不引入测试框架**。用开发服务器手工走查五个 Tab，作为交付前检查项：切换、置灰、计数、导出按钮常驻、
  区间应用与撤销、刷新后区间失效。

## Out of Scope

- 把区间保存为可复用的长期规则、同时存在多个区间、区间重叠时的合并或优先级。
- 把区间外的消费补进区间（例如 9 月 28 日就订好的 10 月 1 日机票）。
- 在区间内再按商户、金额、关键词做二次筛选。
- 把区间并入「分类表快照」一起导出。
- 修改退款配对逻辑，或处理部分退款。
- 响应式布局与移动端适配。
- 修改随手记账单的列结构或格式。
